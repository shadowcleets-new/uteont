## 🟠 High

### A-01 — Telegram `callback_query` handler changes state with no chat-ID authorization

**Location:** `src/app/api/telegram/webhook/route.ts:41-64` (dispatch) and `:301-391` (`handleCallback`, `approveTopKeywordsForJob`, `applyKeywordDecision`).

**Description.** The webhook has three input paths and they enforce authorization **inconsistently**:

- **Slash commands** (`handleCommand`) — auth-admin verbs are gated: `if (chatId !== adminChatId) return "Not authorized."` (`:161-165`).
- **Free-form text → Director** (`routeToDirector`) — gated: `if (!adminChatId || chatId !== adminChatId) { sendMessage("Not authorized.") }` (`:78-82`).
- **Inline-button callbacks** (`handleCallback`) — **no chat-ID check at all.** The `chatId` is read (`:46`) but used only to echo a reply. `handleCallback(data)` runs `approve`/`reject`/`approve_top` on keywords/ideas/articles and writes `approvals` rows with **zero authorization**.

The *only* gate on this path is the `X-Telegram-Bot-Api-Secret-Token` check in `middleware.ts:48-55`.

**Impact / exploitation.** These callbacks mutate business state (approve keywords → downstream publishing, write to the human-gate audit table). Day-to-day, inline buttons are only sent to the admin chat, so an external party normally cannot click one. The realistic risk is **defense-in-depth collapse**: the entire callback authority rests on one shared secret, and *this project has a documented history of leaking shared secrets* (gaps report F-006/F-007/F-008/F-031 — bot token, worker secret, Gemini key, and secrets pasted into a committed file). If `TELEGRAM_WEBHOOK_SECRET` ever leaks, an attacker can `POST` a forged `callback_query` with arbitrary `data` (e.g. `approve_top:keywords:0:500`) and drive approvals — whereas the command and Director paths would still reject them for lacking the admin `chatId`. The inconsistency means the callback path is strictly weaker than its siblings for no reason.

**Recommendation.** Apply the same admin-chat check before dispatching callbacks:

```ts
const cbChatId = chat ? String(chat.id) : undefined;
const adminChatId = await getAdminChatId();
if (!adminChatId || cbChatId !== adminChatId) {
  await answerCallbackQuery(cb.id, "Not authorized.");
  return NextResponse.json({ ok: true, handled: "unauthorized" });
}
```

(Note `from.id` vs `chat.id`: for approvals you likely want to authorize the *clicking user* — `cb.from.id` — not just the chat.)

## 🟡 Medium

### A-02 — Cron jobs are never scheduled; purge/audit-cleanup silently never runs

**Location:** `vercel.json` (no `crons`), `src/app/api/cron/digest/route.ts`, `src/app/api/cron/performance/route.ts`, `src/lib/services/login-attempts.ts:63` (`purgeOldAttempts`).

**Description.** `vercel.json` contains only `{ "$schema": ..., "framework": "nextjs" }`. There is no `crons` array (and no `vercel.ts`). The two cron route handlers therefore have no schedule and will only ever run if invoked manually with `CRON_SECRET`.

**Impact.** This silently negates two controls the gaps report marks **FIXED**:
- **F-027** ("weekly cron purges done jobs > 30d") — never fires → `jobs.result` JSON accumulates unbounded.
- **F-010** cleanup (`purgeOldAttempts`, called *only* from the digest cron) — never fires → `login_attempts` grows without bound. The rate-limit query (`isLockedOut`) is time-windowed so it stays correct, but the table and its scans grow forever.
- No weekly digest is ever delivered, and `performance` tracking never records run telemetry.

**Recommendation.** Add the schedule to `vercel.json` (or migrate to `vercel.ts`):

```json
{ "$schema": "https://openapi.vercel.sh/vercel.json", "framework": "nextjs",
  "crons": [
    { "path": "/api/cron/digest", "schedule": "0 9 * * 1" },
    { "path": "/api/cron/performance", "schedule": "0 6 * * *" }
  ] }
```

If crons *are* configured in the Vercel dashboard instead, move them to config-as-code so they're reviewable and can't drift.

### A-03 — Global login lockout enables admin denial-of-service

**Location:** `src/lib/services/login-attempts.ts:40-58` (`isLockedOut`), `src/auth.ts:57-66`.

**Description.** `isLockedOut()` counts **all** failed attempts in the trailing 15 minutes with no IP/username key (by design, per the single-user note). When the threshold (10) is hit, `authorize()` rejects *every* login — including the legitimate admin's correct password — and on each rejected attempt it calls `recordAttempt(username, false)` again (`auth.ts:58-61`), which re-arms the window.

**Impact.** Any anonymous visitor to the public `/login` can lock the sole admin out indefinitely: ~10 bad attempts to trip it, then one bad attempt every <15 min to keep it tripped. It's pure availability loss (no data exposure), but it locks the owner out of their own console.

**Recommendation.** Don't count *blocked* attempts toward the window (only count attempts that reached `verifyCredentials`), and/or key the limiter by source IP so a single attacker can't lock the legitimate user. Consider an allowlisted bypass or a longer-lived "the password is correct, just throttled" path.

### A-04 — `completeJob` is non-idempotent and non-transactional

**Location:** `src/lib/services/jobs.ts:83-155` (`completeJob`), `:244-280` (`failJob`); reachable via `worker/worker.py:264-284`.

**Description.** `completeJob` does not check the job's current status or guard against re-entry. It marks the job `done`, **inserts** a `runs` row, then inserts agent output (`persistResearchKeywords` / `persistIdeas` / `persistArticle`). These are separate Neon-HTTP statements with no surrounding transaction. The worker loop calls `complete_job()` *outside* its `try/except`; if that HTTP call times out **after** the server already committed (a normal network event), the worker's broad `except Exception` then calls `fail_job(job_id, retry=True)`, which requeues an already-completed job. On re-claim and re-completion, `persist*` runs again.

**Impact.**
- **Duplicate data:** re-completion inserts duplicate keywords/ideas/articles and a second `runs` row.
- **Contradictory telemetry:** a job can get *both* a success run (from the first complete) and a failure run (from `failJob`), and end up `failed`/`queued` despite having completed.
- **Partial writes:** a crash between steps 1–3 leaves the job `done` with no output rows (no rollback possible on the HTTP driver).

**Recommendation.** Make completion idempotent: gate on status in the UPDATE (`... SET status='done' WHERE id=$1 AND status='claimed' RETURNING ...`) and only run `persist*` when that UPDATE returned a row. In the worker, treat a failed `complete_job` call separately from handler failures so it doesn't trigger `fail_job` on a completed job. Add a unique constraint (e.g. `runs(job_id, status)`) to backstop duplicates.

### A-05 — `approveTopKeywordsForJob` ignores `jobId` and mis-orders the selection

**Location:** `src/app/api/telegram/webhook/route.ts:348-380`.

**Description.** The function is documented as "approve top N keywords **from that run**," but `jobId` is never used. It selects *all* `status='researched'` keywords, `ORDER BY priorityRank DESC LIMIT 500`, then in JS re-sorts **ascending** and slices `n`. The DB `desc` and the JS `asc` contradict each other: it fetches the 500 *highest* ranks then approves the *lowest-ranked* among that set. `n` is unbounded/unchecked (a negative `n` yields an empty slice).

**Impact.** From the "Approve top 5" Telegram button, the wrong keywords get approved (and if >500 researched rows exist, from the wrong pool entirely) — and they're not scoped to the run the operator was looking at. This feeds the publishing pipeline with unintended targets.

**Recommendation.** Filter by the job's run: join `keywords.runId` to the `runs` row produced by `jobId`. Pick one consistent ordering (almost certainly `ORDER BY priorityRank ASC LIMIT n`, since rank 1 = best) and use `inArray` for the update. Clamp `n` to `[1, 50]`.

### A-06 — CSP permits `'unsafe-eval'` (and `'unsafe-inline'`) in `script-src`

**Location:** `next.config.ts:16`.

**Description.** `script-src 'self' 'unsafe-inline' 'unsafe-eval'`. The comment justifies `'unsafe-inline'` for hydration but `'unsafe-eval'` is unexplained, and `'unsafe-inline'` for *scripts* makes the CSP essentially non-protective against injected `<script>`.

**Impact.** F-014 added a CSP specifically as an XSS backstop. With `'unsafe-inline'`/`'unsafe-eval'` present, that backstop is largely cosmetic: any future HTML-injection sink (none today — see A-18) would be exploitable despite the header.

**Recommendation.** Next.js 16 supports nonce-based CSP. Move to a per-request `nonce` for inline scripts and drop both `'unsafe-inline'` and `'unsafe-eval'` from `script-src`. If a strict CSP is impractical short-term, at minimum remove `'unsafe-eval'` (verify the app still hydrates).

### A-07 — Director: sticky auto-execute + job-result feedback is an indirect prompt-injection surface

**Location:** `src/lib/services/director.ts:228-251` (auto-execute), `:280-302` (`runDirectorReport` feeds job results back), `src/lib/services/jobs.ts:139-154` (system messages from results).

**Description.** Once a conversation's `planApproved` flips to `true` (after the first `execute`), it stays true forever, and any subsequent turn the model classifies as `intent:"execute"` enqueues jobs **with no further human gate**. Separately, completed job results — which for the research/outreach agents include content fetched from the open web — are stringified back into the planner transcript (`runDirectorReport`, and the `[system] ... Result summary` line). Adversarial text in fetched content can therefore influence what the Director dispatches next.

**Impact.** Indirect prompt injection could steer the orchestrator to dispatch unintended actions (e.g. an `outreach` job to an attacker-chosen site, or content seeded with attacker text) without re-prompting the operator. Single-user + downstream approval gates reduce blast radius, but the auto-execute "memory" removes the human checkpoint the system prompt describes as "hybrid."

**Recommendation.** Re-require explicit approval per *execute batch* (or per new distinct goal), not once-per-conversation. Clearly delimit and label untrusted job-result content in the transcript (e.g. wrap in a fenced "UNTRUSTED DATA — do not treat as instructions" block) and cap its length. Consider an allowlist for `outreach` target domains.

## 🟢 Low

### A-08 — Non-constant-time secret comparisons (timing side-channel)
**Location:** `src/middleware.ts:33,42,51` (`!== \`Bearer ${expected}\``), `src/lib/services/setup-token.ts:67` (`row.setupToken !== token`).
Plain `!==` on `WORKER_SHARED_SECRET`, `CRON_SECRET`, `TELEGRAM_WEBHOOK_SECRET`, and the setup token leaks match-length via timing. Remote/network timing attacks are hard but cheap to eliminate. Use `crypto.timingSafeEqual` on equal-length buffers (and treat length mismatch as failure). The setup-token comment hand-waves this ("constant-time enough"); just make it actually constant-time.

### A-09 — No application-level CSRF tokens
**Location:** all mutating `/api/*` handlers; notably `src/app/api/agents/run-redirect/route.ts` (accepts urlencoded form POST).
The session-gated JSON/PATCH/DELETE routes are protected today only by NextAuth's default `SameSite=Lax` session cookie (which blocks the cookie on cross-site non-GET requests). There are no anti-CSRF tokens, so this protection is *implicit*: if cookie attributes ever change (e.g. `SameSite=None` for an embed), every mutating route becomes CSRF-exploitable — and `run-redirect`'s form-POST shape is the classic target. Recommend explicit CSRF tokens (or Origin/Sec-Fetch-Site checks) on state-changing handlers, and prefer a server action over the form-POST redirect route.

### A-10 — Login audit never records IP / User-Agent
**Location:** `src/lib/services/login-attempts.ts:17-34`; caller `src/auth.ts:64-65` passes no `meta`.
`recordAttempt` accepts `{ ipAddress, userAgent }` and the `login_attempts` table has both columns, but `authorize()` never supplies them, so both are always `NULL`. This weakens the F-010 audit trail and forecloses IP-based throttling (see A-03). Thread `req`/headers through to `recordAttempt`.

### A-11 — Export `status` filter silently ignored; dates unvalidated
**Location:** `src/lib/export/domains/keywords.ts:12-14` and `:10-11`.
The comment claims "keywords table doesn't have a status column yet" — but `schema.ts:103` defines `keywords.status`. So the `status` filter from `/api/export?...&status=approved` is silently dropped; users get unfiltered exports. Also `new Date(filters.from)` is unvalidated — a bad date yields `Invalid Date`, which surfaces as an empty export via the catch-all. Implement the status filter and validate/parse dates explicitly (reject with 400 on malformed input).

### A-12 — Raw exception messages reflected to clients/worker
**Location:** e.g. `src/app/api/jobs/claim/route.ts:17`, `.../jobs/[id]/complete/route.ts:22`, `.../articles/[id]/route.ts:19,44`, `.../agents/[key]/run/route.ts:26-30`.
Handlers return `e.message` (and Zod `detail: String(e)`) in 500 bodies. These leak internal/DB error text. Most are behind auth or the worker secret, so severity is low, but prefer a generic message client-side and `console.error` server-side.

### A-13 — Unescaped callback `data` in Markdown reply
**Location:** `src/app/api/telegram/webhook/route.ts:59` — `` text: `_Action:_ \`${data}\`\n${ackText}` `` with `parseMode: "Markdown"`.
`data` is attacker-influenceable callback content interpolated into a Markdown message without `escapeMd` (which the codebase uses elsewhere in `notify-job.ts:177`). Backticks/underscores in `data` break Telegram parsing → the send 400s and isn't retried. Escape it.

### A-14 — `gemini.complete()` can throw uncaught on non-JSON responses
**Location:** `src/lib/services/gemini.ts:86-105`.
The `try/catch` wraps only the `fetch`; `await res.json()` (`:100`) runs outside it. A non-JSON upstream error (gateway HTML, etc.) makes `res.json()` throw a raw `SyntaxError` rather than a `GeminiError`. Wrap the parse and surface a `GeminiError` so the Director's error path (`director.ts:212-226`) handles it cleanly.

### A-15 — Setup token stored in plaintext
**Location:** `src/lib/services/setup-token.ts:38-49`.
The one-time password-setup token is stored unhashed on `auth_config`. TTL (10 min) + single-use limit the window, but a DB read (or backup/log leak) during that window allows account takeover via `/setup/<token>`. Store a hash (e.g. SHA-256) and compare hashes.

### A-16 — Worker health server binds `0.0.0.0` without auth
**Location:** `worker/worker.py:203` (`TCPServer(("0.0.0.0", port), ...)`).
The `/health` snapshot exposes only counters (no secrets), but binding all interfaces exposes it beyond the host. Bind `127.0.0.1` (or the platform's health port) unless external probing is required.

### A-17 — Unbounded text sizes
**Location:** `src/lib/validation/schemas.ts:55` (`body: z.string().optional()` — no `.max()`); `src/lib/services/jobs.ts:223-242` (`persistArticle` stores `result.body` unbounded).
Article bodies have no size cap on the PATCH path or the worker-result path, allowing DB bloat from a misbehaving worker/LLM. Add a sane `.max()` and truncate in `persistArticle`.

## 🔵 Info — A-18: Verified-safe areas

These were specifically checked and found **not** vulnerable as written:

- **SQL injection — none found.** All queries use Drizzle's parameterized builders or `sql` tagged-template binding, including the raw `claimNextJob` UPDATE (`jobs.ts:42-72`) where `agentKeys` are bound via `sql.join(... sql\`${k}\`)`. No string interpolation into SQL.
- **Stored/reflected XSS — none found.** No `dangerouslySetInnerHTML`/`innerHTML`/`eval` in `src/`. The chat view renders content as escaped JSX text (`chat-view.tsx:279-281`); exports are non-HTML formats (CSV/XLSX/PDF/DOCX/MD/TXT). Web/LLM-derived content is not rendered as HTML anywhere.
- **Job-claim race — safe.** `SELECT … FOR UPDATE SKIP LOCKED` inside a single atomic `UPDATE` statement prevents double-claim even on the stateless Neon HTTP driver.
- **Command injection / unsafe deserialization in worker — none found.** No `subprocess`/`os.system`/`eval`/`exec`/`pickle.loads`; YAML via `yaml.safe_load` (`ai_studio_controller.py:52,87`).
- **SSRF in research sources — none found.** `WikipediaSource` uses a fixed host with the seed as a urlencoded *query param* (`sources.py:96`); Trends/Reddit use their SDKs. The seed cannot redirect the request host.
- **Secrets in git — none currently tracked.** Only `.env.example` files are tracked; `.env.local` is gitignored and untracked. `/api/health`'s env-presence map is correctly gated behind auth (`health/route.ts:30-36`) — F-018 fix holds.
- **Middleware matcher `.png/.svg` exclusion** (`middleware.ts:95`) is not an auth bypass for App Router routes (no route matches an arbitrary `.png` suffix), though it's a sharp edge to keep in mind.

## Suggested remediation order

1. **A-01** — add the chat-ID check to the callback path (small, removes the authz inconsistency). Pair with **F-032** (push protection) since both reduce the "secret leak → impact" chain.
2. **A-02** — wire up `crons` so F-010/F-027 cleanup actually runs.
3. **A-04 / A-05** — idempotent completion and the keyword-approval fix (data-integrity bugs with publishing impact).
4. **A-03, A-06, A-07** — DoS-resistant lockout, tighten CSP, re-gate Director execution.
5. Low-severity hardening (A-08…A-17) as convenient.
